Flaekmig - File and Plugin Documentation
========================================

This document describes the purpose and functionality of the core modules and sample plugins included in this MVP scaffold.

Core
----

- core/models.py
  - Data models and plugin interface.
  - `Target`: represents a scan target (host + metadata).
  - `PortInfo`: simple port record with `port`, `proto`, `state`.
  - `ScanResult`: plugin output container (raw output, parsed ports/services).
  - `Recommendation`: suggested next tool with `tool`, `reason`, `confidence`.
  - `Plugin` (Protocol): required interface for plugins. Plugins should expose:
    - `name`, `description`, `required_binary`, `supported_targets` attributes.
    - `run(self, target: Target) -> ScanResult` to execute the tool.
    - `parse(self, output: str) -> ScanResult` to parse raw output.

- core/rules.py
  - Rule system used by the Engine to produce recommendations.
  - `Rule` dataclass encapsulates a `condition(scan: ScanResult) -> bool` and
    a list of `Recommendation` objects returned when the condition is met.
  - `default_rules()` provides example rules mapping discovered ports to recommended
    follow-up tools (HTTP -> `gobuster`, `nuclei`, `whatweb`; SMB -> `enum4linux`, `crackmapexec`; LDAP -> BloodHound collector).

- core/engine.py
  - Central decision engine coordinating plugins and rules.
  - `Engine` provides:
    - `register_plugin(plugin)` to register plugin instances.
    - `run_target(target_str, plugin_names=None)` to run chosen plugins against a `Target` and evaluate rules.
  - Returns `EngineResult` containing `scan_results` and deduplicated `recommendations`.
  - Checks plugin `required_binary` via `shutil.which()` and skips plugin if binary missing.

- core/workflow.py
  - Minimal workflow utilities.
  - `prioritize(recommendations)` orders recommendations by confidence.

CLI
---

- main.py
  - Minimal CLI entrypoint.
  - Parses a target and optional plugin name list.
  - Creates an `Engine`, registers the sample `nmap` plugin, runs the scan, and prints recommendations.

Plugins
-------

- plugins/__init__.py
  - Packages the plugins folder. Keeps the module importable.

- plugins/nmap/plugin.py
  - Minimal `NmapPlugin` implementation that follows the `Plugin` protocol.
  - Attributes: `name = 'nmap'`, `description`, `required_binary = 'nmap'`, `supported_targets`.
  - `run(target)` executes `nmap -sS -p- -oG - <target>` using `subprocess` and returns parsed results.
  - `parse(output)` extracts port lines from nmap greppable output and builds `PortInfo` objects.
  - Behavior: if `nmap` is not present on the system, `run()` raises `RuntimeError` and Engine will record the failure but continue.

Tests
-----

- tests/test_engine.py
  - Unit test that registers a `FakePlugin` producing ports 80 and 445.
  - Validates that engine rules return expected recommendations (HTTP and SMB related tools present).

Configs & Docs
--------------

- configs/README.md
  - Placeholder for configuration files (JSON/INI). MVP uses no external config by default.

- README.md
  - High-level project overview and design principles.

Usage notes
-----------

- Running the CLI (example):

  python3 main.py 127.0.0.1

- Running tests:

  python3 -m unittest discover -v

Extending the project
---------------------

- Plugins should be small, single-responsibility modules implementing `run` and `parse`.
- Add new rules to `core/rules.py` or supply a rule-loading mechanism (from JSON or Python modules).
- Add dynamic plugin discovery in `core/engine.py` (future improvement) or register plugins explicitly.

Future integrations (non-MVP)
----------------------------

- Local AI / Ollama adapters (optional, disabled by default).
- Neo4j exporter (for Attack Path Analysis / graph storage).
- BloodHound collector wrappers and formatters.

Flaekmig — Machine-Readable System Reference
=============================================

Purpose
-------

This file is intended to be a complete, machine-friendly reference of the Flaekmig
MVP for future automated agents or developers resuming the project. It documents
architecture, runtime behavior, data models, plugin contracts, file locations,
developer workflows, and operational notes. If an LLM or new developer opens this
project, follow the sections below to understand how to run, extend, and test the
system.

Project layout (important files)
--------------------------------

- `main.py` — CLI entrypoint. Accepts a single `target` argument and `--doctor`.
- `core/engine.py` — Decision `Engine` that registers plugins, detects binaries,
  persists simple tool inventory, prompts for installs, runs plugins, and evaluates
  `Rule`s to produce `Recommendation`s.
- `core/models.py` — Data models and plugin `Protocol` definitions (Target, PortInfo,
  ScanResult, Recommendation, Plugin interface).
- `core/rules.py` — Rule definitions and `default_rules()` implementation mapping
  findings to recommended follow-ups.
- `plugins/` — Plugin implementations. Example: `plugins/nmap/plugin.py`.
- `tests/` — Unit tests (currently `tests/test_engine.py`).
- `DOCUMENTATION.txt` — (this file) authoritative machine-readable description.
- `installed_tools.txt` — Generated by `main.py --doctor`; JSON report of detected
  tools. Written next to `main.py`.

Design overview
---------------

1) Plugin-first, minimal core: The system assumes tools are external CLI binaries
   where possible, with optional Python module fallbacks. Each plugin implements
   a small contract and is responsible for invoking the tool and parsing output.

2) Decision Engine responsibility: The `Engine` orchestrates plugins and rules.
   It performs these steps for a run:
   - Detect available tools via `detect_binaries()` (uses `shutil.which()` and
     optional Python import checks).
   - Register plugins (explicit registration via `register_plugin()` in `main.py`).
   - Optionally prompt the user to install missing tools when a plugin is required
     (`ensure_tool()`), supporting `apt` (Debian/Ubuntu), `brew` (macOS), and
     `pacman` (Arch) with a small per-tool mapping and pip/pipx fallback for Python
     packages.
   - Execute each selected plugin's `run(target)` method and collect `ScanResult`s.
   - Evaluate each `Rule` against aggregated `ScanResult`s and return deduplicated
     `Recommendation`s.

3) Rule Engine: Rules are small Python callables packaged into a `Rule` dataclass.
   A rule defines a `condition(scan: ScanResult) -> bool` and a set of `Recommendation`
   objects to return when the condition is met. The Engine applies all rules to
   every `ScanResult` and deduplicates recommendations (keeping the highest
   confidence per tool).

Data models and plugin contract
-------------------------------

See `core/models.py` for canonical definitions. Key points:

- `Target` — factory `Target.from_string(s: str)` will return a typed target with
  `.kind` in {`ip`, `cidr`, `url`, `host`} and `.host` string. Use this when building
  plugin commands.
- `PortInfo` — lightweight dataclass with at least `port: int`, `proto: str`,
  `state: str` and optional `service`/`banner` fields.
- `ScanResult` — contains at least `plugin: str`, `target: Target`, `raw: str` (raw
  output), and a list of parsed `ports: List[PortInfo]` (may be empty if plugin
  failed or produced no ports).
- `Recommendation` — contains `tool: str`, `reason: str`, `confidence: float` (0-1).

Plugin API (what a plugin must expose)
-------------------------------------

Each plugin is a Python module exposing a `Plugin` instance or class following the
`Plugin` Protocol. Minimal expectations:

- Attributes:
  - `name` (str): unique plugin identifier, e.g. `nmap`.
  - `description` (str): short textual blurb.
  - `required_binary` (Optional[str]): CLI binary name the plugin expects (`None`
    if purely Python-based).
  - `supported_targets` (List[str]): list of `Target.kind` values supported.

- Methods:
  - `run(self, target: Target) -> ScanResult`: Execute the tool and return a
    `ScanResult`. Should raise an exception only if the plugin implementation
    itself fails catastrophically — the Engine will catch plugin exceptions
    and include a minimal error `ScanResult` so the run continues.
  - `parse(self, raw_output: str) -> ScanResult`: Idempotent parser that converts
    raw strings into structured `ScanResult` objects.

Engine details and persistence
------------------------------

- `Engine.detect_binaries(tools: Optional[List[str]] = None)` returns a mapping
  of logical tool name to `{"binary": path_or_null, "python": True/False/None}`.
  The `python` field is `True` if a Python module import succeeded, `False` if the
  import was attempted and failed, and `None` if not applicable.
- `Engine.ensure_tool(tool_name: str)` prompts the user to attempt an automatic
  install when a tool required by a plugin is missing. It supports:
  - `apt` (Debian/Ubuntu): `sudo apt-get update && sudo apt-get install -y <pkg>`
  - `pacman` (Arch/Manjaro): `sudo pacman -Syu --noconfirm <pkg>`
  - `brew` (macOS)
  - `pipx` or `pip` for Python modules where appropriate
  The mapping from logical tool name to package name is contained in `core/engine.py`
  and must be extended to add non-trivial package names (e.g., some tools ship as
  `gobuster` vs `gobuster-bin`, or require `go install`). `ensure_tool` will
  re-run binary detection and persist the updated inventory after an attempted
  install.
- `Engine.write_installed_tools_file(path='installed_tools.txt')` persists a
  normalized mapping to the current working directory. The `main.py --doctor`
  command writes a full doctor JSON next to `main.py` as `installed_tools.txt`.

CLI behaviours
-------------

- Running `python3 main.py <target>` will:
  1. instantiate `Engine()`
  2. register the built-in `NmapPlugin()`
  3. detect available tools and print a short summary
  4. run the plugin(s) and print `Recommendation`s

-- Running `python3 main.py --doctor` detects available tools and writes a
  fresh `installed_tools.txt` next to `main.py`. IMPORTANT: `--doctor` will
  NOT attempt to install missing tools — it only generates and overwrites the
  report to reflect current detection. Use the interactive scan run (see
  `run_target`) to allow `Engine` to prompt for installs when required.

Doctor behavior (safety note)
- `--doctor` is read-only with respect to system packages and will not run
  any package manager or attempt installs. This is deliberate to avoid
  modifying the host during an environment check. The generated file
  `installed_tools.txt` always replaces the previous copy.
Install and runtime prompts
---------------------------

The `Engine` exposes `ensure_tool(tool_name: str, attempt_install: bool = False)`
which performs detection and, if requested, will attempt to install a tool using
platform heuristics. Key notes:

- Default behavior (`attempt_install=False`): `ensure_tool` will prompt the
  user interactively before attempting any install. This is the behavior used
  when `run_target()` finds a missing `required_binary` for a plugin — the
  Engine will prompt during a scan run and only attempt installation if the
  user confirms.
- Non-interactive install (`attempt_install=True`): callers can request that
  `ensure_tool` perform an unattended install attempt using `apt`, `pacman`,
  `brew`, or `pipx`/`pip` as appropriate. Careful: unattended installs may
  require elevated privileges and are not used by `--doctor`.
- The internal `pkg_map` in `core/engine.py` contains per-tool package name
  hints for `apt`, `brew`, and `pacman`, plus optional `pip` names for Python
  packages. Maintain and extend that mapping for robust installs across
  distributions (many tools require `go install`/`cargo install` or custom
  packaging; the map is intentionally conservative).

Developer and extension guidance
--------------------------------

1. Adding new plugins:
   - Create a new module under `plugins/<plugin>/plugin.py` implementing the
     plugin contract. Keep `run()` and `parse()` small and unit-testable.
   - Register the plugin in `main.py` (or extend `Engine.load_plugins_from_package`
     to discover them automatically).

2. Rules:
   - Add new `Rule`s in `core/rules.py` as data-driven Python constructs.
   - Keep rules deterministic and idempotent: they should only depend on
     `ScanResult` content and not external state.

3. Persistence and CI:
   - `installed_tools.txt` is intentionally simple JSON. For more robust
     workflows, migrate to a TOML/SQLite or a `~/.flaekmig` cache file and add
     an explicit command to refresh it.

4. Tests and mocks:
   - Tests should avoid running external binaries. Use a `FakePlugin` pattern to
     produce deterministic `ScanResult`s and assert rules/engine outputs.
   - For `ensure_tool()` tests, mock `subprocess.run`, `shutil.which`, and `input()`.

Operational notes and caveats
----------------------------

- The `ensure_tool()` automatic installer is intentionally conservative and
  heuristic. Different Linux distributions may require different package names
  or installation methods (`snap`, `flatpak`, `go install`, `cargo install`).
  Extend the `pkg_map` in `core/engine.py` for each tool you care about and add
  per-distribution overrides as needed.
- For unattended or CI environments, do not rely on `ensure_tool()` interactive
  prompts. Instead, populate `installed_tools.txt` manually or use the `--doctor`
  output during provisioning.
- Python runtime: This project is tested with Python 3.9 but aims to be
  cross-compatible with 3.8+. Use the `scripts/setup_env.sh` to create a venv and
  `pip install -r requirements.txt` to prepare the environment.

Quick reference (developer commands)
-----------------------------------

Create virtualenv and install deps:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Run the doctor:

```bash
python3 main.py --doctor
```

Run unit tests:

```bash
python3 -m unittest discover -v
```

Next recommended improvements
---------------------------

- Expand `pkg_map` in `core/engine.py` with correct package names and non-apt
  installation workflows (e.g., `go install` for `gobuster` in many cases).
- Add non-interactive `--yes` flag to `ensure_tool()` for scripted installs.
- Add unit tests around doctor persistence and `ensure_tool()` using mocks.
- Implement dynamic plugin discovery with entry points or a lightweight plugin
  manifest file.

If a new LLM session opens this repository, the agent should:

1. Read `DOCUMENTATION.txt` (this file).
2. Run `python3 main.py --doctor` to collect environment facts and persist
   `installed_tools.txt`.
3. Run tests with `python3 -m unittest discover -v` to validate basic behavior.
4. Inspect `core/engine.py` and `core/models.py` for plugin and rule contracts
   before attempting to modify or add plugins.
